# Orchestrator: Role Routing & Council Mode

This file is the brain map the agent consults to decide which skill(s) to load for a given task,
and how several should combine when more than one applies. It holds no role expertise itself;
see the individual `SKILL.md` files for that.

## 1. Skill Index

Skills are grouped by **tier** (set in each skill's `metadata.tier`, defined in the master's
`catalog.json`). **Persona Roles** model a job's perspective. **Mandatory Process Skills** govern
*how* work is done in any codebase. The **Agent Constitution** shapes how every routed role
investigates, verifies, and escalates. **Practice**, **Supporting**, and **Cloud** skills apply only
when the task shape matches. `documentation-maintainer` and `logging-standards` have a deliberately
broad footprint: consider them on most non-trivial changes *alongside* whichever roles are triggered.

In a project copy this index lists exactly the skills installed there; `skillpack` regenerates it
on every install or update. Project-only skills are listed in this file's project-tailoring block
(see §7), never inside the generated region.

### A note on overlapping pairs in the Practice Skills

Several practice skills sit next to an existing role with a related footprint. They are designed

- `deployment-strategy` (how this change rolls out) ↔ `devops-engineer` (builds/runs the pipeline) ↔ `release-manager` (what ships, go/no-go)
- `secrets-and-config-hygiene` (where values may live) ↔ `codebase-security-auditor` (nothing sensitive leaves the machine — always outranks) ↔ `gcp-secret-manager` (backend mechanics)
- `dependency-data-risk-audit` (does this dependency leak or train on data) ↔ `license-compliance-checker` (may we legally use it)

## 2. Auto-Trigger Rules (the 3-signal model)

Three independent signal types feed routing:

- **(a) Intent/keyword signal** — the user's task description contains, or closely paraphrases,
  a role's trigger keywords.
- **(b) File/path signal** — the files being read, created, or edited match extensions or paths
  conventionally owned by a role (e.g. `*.tf`/`Dockerfile`/`.github/workflows/*` → DevOps;
  `*.sql`/migration folders → Database Engineer/DBA; `*.test.*`/`*.spec.*`/`e2e/` → QA).
- **(c) Project-context signal** — the detected tech stack (via the Stack Detection &
  Adaptation clause each skill carries — inspect `package.json`, `requirements.txt`, `go.mod`,
  `Gemfile`, `pom.xml`, `Dockerfile`, CI config, and file extensions present) is consistent with
  that role's domain (e.g. a `Dockerfile` + `.github/workflows/` present raises DevOps
  relevance even before any keyword is typed).

**Heuristic — load a role when at least 2 of the 3 signals point to it.** A single strong
keyword match alone (1 signal) is not enough to load a role uninvited; but 2-of-3 (e.g.
keyword + file path, or file path + stack context) is sufficient. If only one signal is
present but it is very strong and unambiguous (e.g. the user explicitly says "as the DBA,
review this migration"), that counts as an explicit override and loads the role directly.

If **zero roles** clear the 2-of-3 bar, proceed with default engineering judgment — do not
force-load a role that doesn't fit; a generic response grounded in the codebase is correct.

If **exactly one role** clears the bar → **single-skill mode**: apply that role's lens directly,
no council needed.

If **two or more roles** clear the bar → evaluate for **council mode** (below).

### 2a. Exception: Non-Negotiable Skills (Codebase Security Auditor)

`codebase-security-auditor` does not use the 2-of-3 heuristic above. **A single signal —
one keyword, one file touched, one outbound call constructed, one dependency added — is
sufficient to activate it, every time, with no exceptions.** This is a deliberate departure from
the standard model:

- It is never held back pending a second corroborating signal.
- It is never something the user can talk down, defer, or opt out of mid-task by framing the
  request as low-risk, casual, or urgent — no phrasing of a request waives it.
- It is never deprioritized because zero or one other roles are active — it runs regardless of
  whether council mode is otherwise warranted.
- It runs **in addition to** whichever persona role(s) or other process skill(s) are triggered,
  never as a replacement for them and never sequenced after them ("we'll check security later").

If this skill finds a real risk (an actual secret, an actual exfiltration-shaped outbound call,
an actual malicious-dependency signal), it blocks or redacts before other work proceeds — it
does not merely note the concern for later consideration. See its own `SKILL.md` for the
concrete triggers and remediations, grounded in real-world exfiltration techniques (secrets in
git history, supply-chain/dependency attacks, network/webhook exfiltration, prompt-injection-
driven data leakage, local environment leakage, CI/CD leakage).

### 2b. Exception: Non-Negotiable-Once-Triggered Skills (Codebase Visualizer)

`codebase-visualizer` is a different kind of exception from `codebase-security-auditor`. It is
**not** always-on — it only activates when a task genuinely calls for seeing structure rather
than reading a description of it (see its own Trigger Signals). But **once that condition is
met, it is non-negotiable**: Claude Code must not substitute a prose explanation, an ASCII
sketch, or a description "of what the diagram would show" in place of actually running the
skill's static-analysis-and-render pipeline and producing the real `.html` artifact. It is also
non-negotiable in *how* it satisfies the request — it must not skip straight to describing
structure from having read the files, skipping the real static-analysis tool call, even if that
would be faster. In short: the decision of *whether* to visualize follows normal judgment; the
execution *once visualizing is warranted* does not admit shortcuts.

### 2c. Exception: Single-Signal Gate (Dependency Data-Risk Audit)

`dependency-data-risk-audit` is gated on one specific event — **a new dependency being
introduced** (a manifest entry, a CLI tool or IDE extension, an MCP server, a CDN resource, a
third-party API/SDK), including one-off or temporary use. Any single such signal activates it; no
second signal is required. It is not always-on like §2a: it stays dormant until something new is
introduced. Once it fires, it always runs alongside `codebase-security-auditor`, never instead
of it.

### 2d. Always-consulted constitution

`agent-operating-principles` and `agent-verification-and-guardrails` (Agent Constitution
group) are not routed by the 2-of-3 model at all — they apply to every non-trivial task as the
manner in which routed roles work. They never add a visible voice in council mode; they shape
how the synthesized answer is investigated, verified, and reported (for example, the mandatory
"not verified" section of a completion report).

## 3. Council Mode (Team Simulation) Rules

Council mode activates when a task is cross-cutting (multiple roles cleared the 2-of-3 bar) or
is explicitly ambiguous/high-stakes even under a single role (e.g. a schema change with
production data implications). Claude Code adaptively chooses the interaction pattern based on
task shape — this is a judgment call, not a fixed lookup, but here is the concrete grounding:

- **Sequential handoff** — use when the task has a natural pipeline order, where one role's
  output is the next role's input.
  - Examples: shipping a new feature (Backend builds → QA tests → DevOps deploys); a schema
    change (Database Engineer/DBA designs → Backend integrates → SRE validates rollout safety);
    a new ML feature (Data Scientist prototypes → ML Engineer productionizes → MLOps deploys/monitors).

- **Parallel independent review** — use when multiple roles need to weigh in on the same
  artifact with no natural ordering between them.
  - Examples: reviewing a new API design (Backend + Security + API Test Specialist all review
    the same spec independently); a new UI feature touching sensitive data (Frontend + Security
    + Technical Writer review the same PR); an architecture proposal (Software Architect +
    Solutions Architect + SRE weigh in independently on the same doc).

- **Debate/critique** — use when roles are likely to have genuine tension or conflicting
  optimization targets on the same decision.
  - Examples: "ship fast vs. add more test coverage" (Technical Delivery Manager vs. QA); a
    denormalization proposal for performance (Backend/Performance concern vs. Database
    Engineer/DBA data-integrity concern); a proposed relaxation of a security control for
    velocity (Security/AppSec vs. DevOps/Delivery).

Pick the pattern that matches the task's actual shape; do not default to one pattern out of habit.

## 4. Council Mode Output Behavior (critical)

In council mode, Claude Code must **never expose the individual role "voices," internal
disagreement, or role-play commentary to the user.** The multi-perspective process runs
silently — internally, roles' concerns are gathered and reconciled — and the user only ever
sees **one single, clean, synthesized recommendation or output**, written as if one senior
engineer had already considered every angle. Do not narrate "the DevOps role says X, but the
Security role says Y" in normal output; resolve internally and state the resolved answer,
optionally with a brief note on a real tradeoff that was made (see §5).

## 5. Conflict Resolution — General Tiebreaker Hierarchy

**Rank 0, above all else and not actually a tiebreaker input: sensitive data must never leave
the local machine.** This is `codebase-security-auditor`'s domain (§2a) and it is a
*precondition* on every other rank below, not one more consideration weighed against them — no
outcome from ranks 1-5 is acceptable if achieving it requires letting a secret, credential, PII,
or proprietary code exit the machine without the user's specific, informed confirmation of that
exact transfer. This is never overridden by "the user asked for it casually" or by any other
role's optimization target.

When two roles' concerns genuinely conflict *within* that boundary and no principled
reconciliation is obvious, apply this general priority order, in this order, unless the user's
explicit instructions for the task at hand state otherwise:

1. **Production safety / data integrity**
2. **User-facing correctness**
3. **Security hardening**
4. **Performance**
5. **Developer convenience / speed**

When a conflict is genuinely unresolvable by principle even after applying this order, default
to the **most conservative (lowest-risk) option**, and briefly note the tradeoff that was made
so the user understands what was traded away — without exposing the underlying simulated debate.

## 6. Notes for maintainers of the master library

- **One source, generated indexes.** Skills live flat in the master's `skills/<name>/`. The index in
  §1, the library README, the counts in the root README, and the `AGENTS.md` block written into
  projects are all generated from frontmatter by `python tools/skillpack build`; CI runs
  `build --check` and `validate`. Adding a skill means adding one folder; nothing else is
  hand-registered.
- **Mandatory process skills** must exist in the master regardless of what future persona research
  finds: they encode baseline engineering hygiene, not project knowledge. `codebase-security-auditor`
  must never be removed or weakened in any copy (§2a/§5), and `codebase-visualizer`'s
  execute-once-triggered guarantee (§2b) must be preserved. `skillpack` always installs the
  orchestrator, both constitution skills, and `codebase-security-auditor`, whatever subset is asked for.
- **Supporting skills** (`agent-browser`, `playwright`, `interactive-artifact-diagrams`, `ponytail`) are
  conditional. Each is a reference for one tool or add-on; keep it only where that tool is really used,
  because a stub with nothing behind it misleads the skills that delegate to it. `ponytail` is
  optional and installed only on request (`--with ponytail`).
- **Third-party skills** (`agent-browser`, `ponytail`) are vendored verbatim and listed in
  `skills-lock.json` and `catalog.json`. The library's own additions sit inside a
  `<!-- library-notes:begin -->` / `<!-- library-notes:end -->` block; `skillpack validate` fails if the
  upstream text outside that block changes. A third-party skill never outranks ranks 0-3 of §5.
- **`gcp-skill-builder`'s output varies per project by design** (a project on Cloud Run and BigQuery
  accumulates different `gcp-*` skills than one on GKE and Pub/Sub). The generator itself stays
  consistent across copies. A generated skill worth keeping everywhere is generalised into the master.
- **Verify-current-facts skills.** `dependency-upgrade-manager`, `license-compliance-checker`,
  `api-contract-checker`, `onboarding-guide-generator`, and `codebase-setup` must never rely on a
  snapshot of tooling, regulatory text, or changelogs baked in at authoring time. Preserve that
  discipline in any edit.
- **Never put project specifics in the master**: commands, ports, hostnames, table and class names,
  branch names, incident dates, people. They belong in a project copy's tailoring block or memory notes.

## 7. Project copies: tailoring, trimming, and drift

- **Tailoring lives in one place per skill.** Put project facts at the end of a `SKILL.md`, between
  `<!-- project-tailoring:begin -->` and `<!-- project-tailoring:end -->`, or in files under the skill's
  `project/` folder. `skillpack update` replaces the master part of a skill and keeps both. An edit
  anywhere else marks the skill as tailored outside the block, and updates stop for it until someone
  merges by hand.
- **Project-only skills** go in their own folders. List them in this file's tailoring block, numbered
  or grouped after the generated index (a "this copy only" table), so master rows can change without
  collisions. If one holds reusable practice, generalise it into the master (strip names, paths,
  incidents); otherwise acknowledge it with `skillpack acknowledge` so drift reports stop flagging it.
- **Trimming is remembered.** Deleting a skill folder (or `skillpack install --exclude name`) records it
  as excluded, and later installs never re-add it uninvited. Record *why* a skill was left out in this
  file's tailoring block ("checked and left out on purpose: X, because ..."), so the next maintainer
  does not re-add it or re-litigate the decision.
- **Shadowing.** In Claude Code a personal skill in `~/.claude/skills/<name>/` wins over a project
  skill with the same name, so the project's copy (and its tailoring) is silently ignored. If a
  project tailors a skill that is also installed personally, remove the personal copy on that machine
  or move the project rules into the project's `CLAUDE.md`.
- **Drift.** `skillpack check --target .` reports skills that are new in the master, updatable,
  tailored outside their block, or project-only. The optional SessionStart hook (the master's `templates/claude/hooks/skill_drift.py`, installed as `_templates/` for Claude Code only)
  runs the same check at the start of each session.

## 8. Grounding: SWEBOK, lifecycle, and the economics behind the process

Background, not a per-task lookup. It explains why the library is shaped the way it is.

**SWEBOK v4's 18 knowledge areas** are the closest thing the field has to an agreed scope statement,
and the completeness checklist this library maps onto: Software Requirements, Architecture, Design,
Construction, Testing, Engineering Operations, Maintenance, Configuration Management, Engineering
Management, Engineering Process, Models and Methods, Quality, Security, Professional Practice,
Engineering Economics, Computing Foundations, Mathematical Foundations, Engineering Foundations.
Three are new in v4 (Architecture, Security, Operations), which signals architecture as a first-class
activity, security as engineering rather than a review gate, and operations as inseparable from
development. An agent that writes code but represents none of configuration management, economics,
or professional practice is a code generator, not an engineer.

**Lifecycle models are sequencing strategies, not different phases.** Waterfall, V-model, incremental,
spiral, agile, and continuous delivery all pass through the same phases (planning, requirements,
architecture and design, construction, testing, release, operations); they differ in batch size,
feedback latency, and how much is decided up front. Most teams run a hybrid: a governance shell (the
phase gates in `agent-operating-principles`), a short iterative rhythm, and automation underneath
(`deployment-strategy`, `devops-engineer`). Royce's 1970 paper, the origin of the "waterfall" diagram,
argued *for* feedback between phases; the rigid reading came later. Process models flatten into
their most bureaucratic reading unless someone keeps the feedback loops alive, which is why the phase
machine treats going back to an earlier phase as normal.

**The economics.** The cost of fixing a defect rises sharply with the phase in which it is found: a
misunderstanding caught while clarifying costs a conversation; caught in production it costs a
release, a migration, maybe a customer. That is the whole argument for shift-left testing, security,
and requirements clarity, and for `requirements-engineering`'s clarity gate: an agent that asks before
building is working at the cheapest point on the cost curve. Defects in non-functional properties
(performance, security, maintainability) are a large share of all defects, which is why
`requirements-engineering` treats ISO/IEC 25010 quality characteristics as seriously as functional
requirements.
